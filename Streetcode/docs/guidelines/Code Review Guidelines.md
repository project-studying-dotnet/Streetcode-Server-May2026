
# Code Review Guidelines

## 1. Коли потрібно використовувати Request Changes

`Request Changes` використовується лише у випадках, коли Pull Request:

* містить баги
* ламає існуючий функціонал
* не проходить build/tests
* містить критичні проблеми безпеки
* порушує agreed project conventions

---

## 2. Коли використовувати comments / suggestions

`Comments / suggestions` використовуються у випадках, коли Pull Request містить:

* форматування коду:

  * переноси рядків
  * відступи
  * розташування дужок
* проблеми з пробілами:

  * порожні рядки
  * зайві або відсутні пробіли
* особисті стилістичні вподобання reviewer’а
* невеликі пропозиції щодо назв:

  * змінних
  * методів
  * файлів
* покращення структури коду, яке не є обов’язковим для роботи функціоналу
* попередження Sonar, які не впливають на:

  * логіку
  * безпеку
  * стабільність коду

---

## 3. Якщо reviewer залишив Request Changes

Reviewer зобов’язаний:

* слідкувати за Pull Request до моменту виправлення проблем
* повторно перевірити PR після внесення змін
* зняти blocking review після виправлення проблем

> Статус "не черговий" не є причиною не знімати Request Changes.

---

## 4. Етика Code Review

Code review має бути спрямований на покращення якості коду, а не на особисті суперечки.

### Коментарі під час review повинні бути:

* конструктивними
* аргументованими
* професійними

### Не допускається:

* блокування Pull Request через особисті конфлікти
* блокування PR через некритичні стилістичні зауваження
* безстрокове блокування роботи команди через незначні або косметичні зауваження

---

# 5. Політика SonarQube

## До blocking issues належать:

* blocker
* critical
* проблеми, що впливають на функціональність
* security vulnerabilities

---

## До non-blocking issues належать:

* warnings, пов’язані з whitespace
* warnings, пов’язані виключно з форматуванням
* косметичні стилістичні зауваження

---

## Команда може колективно прийняти рішення:

* вимкнути певні Sonar rules
* знизити їх рівень важливості (severity)
* перевести їх в informational category

---

## 6. Auto Merge

Дозволяється використовувати Auto Merge, якщо:

* усі required checks успішно пройдені
* отримані необхідні approvals
* відсутні blocking reviews

---

## 7. Після merge Pull Request необхідно

* оновити інші активні гілки
* синхронізувати зміни відповідно до branch hierarchy

---

## 8. У випадку конфлікту між reviewers

* обговорення ведеться в PR comments
* якщо консенсусу не досягнуто — питання виноситься на командне обговорення
* рішення приймається колективно або відповідальною особою проєкту

---

## 9. Рівність правил

Усі погоджені conventions та правила однаково застосовуються до всіх учасників проєкту без винятків.
