# Правила закриття issues на GitHub

Issues знаходяться тут: https://github.com/orgs/project-studying-dotnet/projects/29. <br />

## Вибір завдання
1. Усі вільні issues знаходяться в колонці "Backlog". Переглядаєте та вибираєте те, що вам цікаво.
2. Призначаєте себе як assignee.
3. В частині "Projects" вибираєте статус "ToDo".
4. Вибираєте story point для "Estimate", якщо issue немає sub-issues. <br />

> Story point - це умовна одиниця вимірювання складності задачі. Вона не має конкретного значення, 
але зазвичай використовується для оцінки часу, необхідного для виконання задачі.
Вибирайте story point відповідно до вашого розуміння складності задачі та вашого досвіду.
Варіанти наступні:
> - (1) займає декілька годин
> - (2) займає 1-2 дні
> - (4) займає пів тижня
> - (8) займає тиждень
> - (16) займає більше тижня

## Підготовка завдання
В нашому випадку завдання можуть потребувати коректування. Перед тим, як приступати до виконання завдання, 
варто спочатку переглянути стан проєкту та визначити конкретні кроки, які потрібно виконати для реалізації завдання.
Можливо дещо вже було виконано, або ж навпаки, потрібно буде виконати додаткові кроки, які не були описані в завданні.
На основі аналізу ви можете підкоректувати завдання, змінивши його назву, опис, "Labels", "Type", "Estimate" та інші параметри, окрім "Sprint".
Ви також можете робити sub-issues, якщо вважаєте, що його можна розбити на декілька підзадач.
Головне - не змінювати ціль/мету завдання, інакше варто створити нове завдання.

## Створення завдань
За потреби ви можете створити завдання.
1. Робите для нього назву та опис.
2. Задаєте "Labels" та "Type".
3. Вибираєте наший борд в "Projects".
4. Вибираєте статус "Backlog".
5. Задаєте "Sprint".

Ви можете створювати "Labels" за потреби.
Ви можете додавати префікси до назви issue, якщо потрібно.

2. Створити окрему гілку для завдання (в github чи visual studio).

### Гілки
Гілка повинна мати "dev", як базову гілку. Назва гілки повинна мати наступний формат:
```
<type>/<номер issue>/<назва issue (коротко)>

де <type> - це тип завдання:
1. (feat) - для завдань
2. (fix) - для виправлення багів
3. (test) - для тестів
4. (chore) - для змін в самому проєкті чи рішенні
5. (refactor) - для рефакторингу коду
6. (docs) - для документації
7. (ci) - для змін в CI/CD

де <номер issue> - це номер завдання.
де <назва issue (коротко)> - це коротка назва завдання, яка відображає його суть.
Вона повинна бути зрозумілою та інформативною, але не надто довгою. Використовується kebab-case
```

### Коміти
Назва коміту повинна починатись із назви гілки, без назви issue. Вміст коміту повинен відповідати наступному формату: https://www.conventionalcommits.org/en/v1.0.0/
```
feat/29: Implemented user login functionality with JWT authentication

Additional text (optional)
```

### Оновлення проєкту
Протягом виконання завдання, у "dev" гілку будуть періодично мерджитись інші гілки.
Періодично оновлюйте локальну "dev" та вашу гілки. Чим частіше, тим краще.

## Створення Pull Request
Після того, як ви виконали завдання, потрібно створити Pull Request (PR) для злиття вашої гілки з "dev".
1. Перед цим обов'язково синхронізуйте "dev" та вашу гілку та, за потреби, вирішіть конфлікти.
2. Впевніться, що ви зробили push/sync вашої гілки.

Створювати PR рекомендується на GitHub (вам навіть з'явиться відповідна пропозиція там).
1. Ім'я PR повинно збігатися з назвою issue, яке воно закриває, або принаймні бути відповідним.
2. В описі PR потрібно вказати, що саме було зроблено або що ми отримуємо після злиття цього PR.
3. В PR потрібно вказати, яке issue воно закриває. Для цього в кінці опису потрібно написати "Solves/Closes/Fixes #<номер issue>".
   Інший спосіб - це вибрати issue в частині "Development".
4. Вказати усіх assignees, які брали участь у виконанні завдання.
5. Вказати в reviewers нашу команду, а не конкретних учасників.
6. Не вказувати "Labels" та "Projects".
7. Перевірити вказані issues на відповідність умовам розділу (Вибір завдання).
8. Ваший PR повинен пройти перевірки Sonar. За замовчуванням, проблем повинно бути 0. Якщо ви проти, звертайтесь до скрам-майстра.
9. Коли у "dev" гілку будуть мерджитись інші PR, ваший PR потрібно буде оновити, щоб його можна було замерджити.
   Оновити PR може reviewer, однак вирішування конфліктів на плечах автора PR.
10. Змініть статус відповідних issues на "In review".

Коли всі пункти виконані, можете повідомити про ваший PR у діскорді в каналі "review-pull-requests"
https://discord.com/channels/1462723713366626462/1462723714671181945.
На цьому ваша робота не закінчується.

## Перегляд PR
Reviewers можуть зробити "change request" заблокувавши ваший PR. Ви повинні зробити відповідні зміни.
Ви можете приймати коміти, запропоновані reviewers. Resolve conversation може натискати тільки той, хто його відкрив.
Виконання прохань коментарів на ваш розсуд. Якщо ви вважаєте блок несправедливим, звертайтесь до скрам-майстра.

## Мердж PR
Коли усі умови виконані, ви можете замерджити PR.
Після мерджу, видаліть вашу гілку. Після цього ваша робота буде завершена.
